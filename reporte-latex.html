1. Definición del problema

Las organizaciones que operan infraestructuras distribuidas —ya sea por la presencia de múltiples sucursales, servicios desplegados en distintas ubicaciones o personal remoto— requieren mecanismos confiables para interconectar nodos de manera segura. Las redes privadas virtuales (VPN) constituyen una solución adoptada para este fin, y protocolos como WireGuard han ganado popularidad debido a su simplicidad, desempeño y modelo criptográfico moderno.

Si bien WireGuard resuelve eficazmente el cifrado y transporte del tráfico, no aborda de forma nativa los problemas de orquestación, gestión de estado y operación a escala. En escenarios donde el número de nodos crece o donde la topología de red cambia dinámicamente, la administración manual de configuraciones, claves y rutas se vuelve propensa a errores, difícil de auditar y costosa en términos operativos.

Las soluciones existentes para la gestión de VPN suelen presentar al menos una de las siguientes limitaciones: dependencia de interfaces gráficas, uso extensivo de secretos estáticos, dependencias de terceros y registro por email. Estas limitaciones dificultan su adopción en entornos automatizados o con requerimientos estrictos de seguridad y auditabilidad.

El problema que aborda LinkGuard es, por tanto, la falta de un mecanismo ligero y explícito para orquestar redes WireGuard de manera segura, declarativa y tolerante a fallos, manteniendo claridad en el modelo de control y evitando complejidad innecesaria en los nodos finales.

2. Usuarios y casos de uso

LinkGuard está orientado a usuarios técnicos que requieren gestionar conectividad segura entre nodos sin delegar completamente el control a soluciones opacas. Los usuarios objetivo incluyen:

  • Administradores de sistemas y redes, responsables de operar infraestructuras distribuidas y mantener conectividad segura entre servidores, sucursales o entornos híbridos.
  • Entornos académicos o de laboratorio, donde se busca experimentar con topologías de red y mecanismos de control sin la sobrecarga de soluciones comerciales.

A partir de estos perfiles, se identifican los siguientes casos de uso principales:

  • Incorporación dinámica de peers: un nodo puede registrarse automáticamente en la red y obtener su configuración sin intervención manual.
  • Gestión centralizada de topologías: definición y modificación de redes, asignación de direcciones IP y rutas desde un punto único de control.
  • Separación de responsabilidades: los nodos finales no deben poseer credenciales con alcance administrativo ni conocimiento global del sistema.

3. Requerimientos funcionales

RF-01 Registro de peers

El sistema debe permitir el registro de peers mediante tokens de activación, asociando de forma única cada peer a una identidad interna, de forma que un nodo solo puede pertenecer a una red por limitación de alcance y diseño (en trabajo a futuro sería posible tener múltiples interfaces).

✔ Criterio de verificación: el peer queda registrado y es consultable por el orquestador.

RF-02 Asignación automática de direcciones IP

El sistema debe asignar automáticamente una dirección IP del túnel a cada peer dentro del rango definido para la red correspondiente, evitando colisiones.

✔ Criterio de verificación: cada peer recibe una IP única dentro del CIDR configurado.

RF-03 Gestión de redes virtuales

El sistema debe permitir la creación, consulta y eliminación de redes VPN, cada una con su propio espacio de direcciones y configuración.

✔ Criterio de verificación: las redes pueden administrarse de forma independiente y no interfieren entre sí.

RF-04 Distribución de configuración

El orquestador debe generar y distribuir la configuración WireGuard correspondiente a cada peer, incluyendo claves públicas, endpoints y AllowedIPs.

✔ Criterio de verificación: el peer puede aplicar la configuración y establecer un túnel funcional.

RF-05 Actualización de configuración

El sistema debe permitir la actualización incremental de la configuración de los peers cuando se produzcan cambios en la topología o en los parámetros de la red.

✔ Criterio de verificación: el peer detecta cambios y aplica únicamente las modificaciones necesarias.

RF-06 Revocación de peers

El sistema debe permitir la eliminación de un peer, impidiendo su participación futura en la red.

✔ Criterio de verificación: el peer eliminado no puede establecer túneles ni intercambiar tráfico.

RF-07 Monitoreo de estado

El sistema debe mantener información básica del estado de los peers, como actividad reciente o conectividad.

✔ Criterio de verificación: el orquestador puede identificar peers activos e inactivos.

RF-08 Interfaces de administración

El sistema debe ofrecer interfaces de administración (CLI) para la gestión de redes, peers y configuraciones.

✔ Criterio de verificación: las operaciones administrativas pueden realizarse sin acceso directo a todo el sistema.

4. Requerimientos no funcionales

RNF-01 Seguridad

El sistema debe garantizar la confidencialidad e integridad de las comunicaciones, apoyándose en los mecanismos criptográficos de WireGuard y en controles de acceso para el plano de control.

RNF-02 Aislamiento

El sistema debe asegurar el aislamiento entre redes y usuarios, evitando accesos no autorizados.

RNF-03 Persistencia del estado

El orquestador debe mantener un estado persistente, de modo que la información crítica sobreviva a reinicios del sistema.

RNF-04 Observabilidad

El sistema debe proporcionar registros y métricas suficientes para diagnosticar fallos y evaluar su comportamiento.

RNF-05 Reproducibilidad

El sistema debe poder ser desplegado y probado en entornos controlados siguiendo procedimientos documentados. Debe ser posible replicarlo tanto con dispositivos virtuales como dispositivos físicos; tanto expuestos a internet como detrás de NAT o con IP ruteables.

RNF-06 Mantenibilidad

El diseño del sistema debe favorecer la extensión y modificación futura, permitiendo incorporar nuevas funcionalidades sin reescrituras completas.

5. Restricciones técnicas y operativas

Las restricciones técnicas y operativas del sistema LinkGuard se dividen principalmente en requisitos de entorno, límites de configuración (cuotas) y condiciones de conectividad de red. Con el fin de mantener simplicidad, se decidió evitar dependencias externas obligatorias, como bases de datos o sistemas de mensajería.

5.1 Requisitos del sistema

El sistema operativo debe ser Linux, compatible con distribuciones que utilicen systemd (Debian, Ubuntu, Fedora, RHEL, CentOS, Arch, openSUSE, Alpine). Usa los manejadores de paquetes: apt, dnf, yum, pacman, zypper, apk. El instalador fallará si systemctl no está disponible.

5.2 Software y dependencias

  • Python: Requiere versión 3.8 o superior junto con pip, python3, python3-pip, python3-venv.
  • Librerías utilizadas: PyJWT >= 2.7.0. El resto son parte de la biblioteca estándar de Python 3: argparse, hashlib, ipaddress, json, logging, os, secrets, socket, ssl, subprocess, sys, threading, time, xmlrpc, socketserver, typing.
  • WireGuard: Es imprescindible tener instalado wireguard-tools (wg y wg-quick).
  • Utilidades: El sistema depende de curl, ca-certificates, openssl e iptables (o iptables-nft).
  • Privilegios: Tanto la instalación como la ejecución del daemon deben realizarse como root (o con sudo), ya que se requiere manipular interfaces de red.

5.3 Restricciones operativas y de configuración

  • Máximo de 50 peers por red/tenant. Máximo de 10 redes gestionadas.
  • Los tokens de sesión JWT tienen una duración corta (por defecto 10 minutos o 600 segundos); el agente debe renovarlos automáticamente antes de que expiren para mantener la conectividad.
  • Un peer se marca como inactivo si el orquestador no recibe un heartbeat en un periodo de 180 segundos (HEARTBEAT_TTL_SEC). El intervalo estándar de envío de heartbeat es cada 25 segundos.
  • El orquestador no arrancará si detecta tokens de administración (ADMIN_TOKEN) o de usuario con valores por defecto inseguros (ej: 12345, password).
  • Cada peer solo tiene una red dado que el agente solo soporta una interfaz de WireGuard.
  • El orquestador solo puede ser una instancia dado que no admite balanceo.

5.4 Restricciones de red y conectividad

Puertos obligatorios

  1. TCP 8000: Debe estar abierto para el acceso a la API XML-RPC del orquestador.
  2. UDP 51820: Puerto estándar de WireGuard que debe ser accesible para el tráfico del túnel.

Limitaciones por topología

  1. Mesh puro: Todos los peers deben tener una IP pública o estar detrás de un NAT full-cone. Si un peer tiene NAT simétrico, no podrá establecer conexiones directas en esta topología.
  2. Hub-Spoke: Los nodos remotos no necesitan IP pública, pero el tráfico está restringido a pasar siempre por el hub.
  3. Hub-Mesh: Esta topología combina elementos de mesh y hub-spoke, permitiendo que algunos nodos tengan conectividad directa mientras otros dependen del hub.

5.5 Seguridad y permisos

El peer no podrá registrarse ni operar si la variable ORCH_TOKEN no tiene un valor válido proporcionado por el administrador. Archivos sensibles como peer.env y las claves privadas deben tener estrictamente permisos 600 (solo lectura para root).

5.6 NAT, forwarding y utilidades del sistema

Para soportar conectividad entre redes y salida a Internet cuando aplica, el hub-agent configura reglas de iptables y habilita IP forwarding vía sysctl. El flujo garantiza reglas base (FORWARD y NAT MASQUERADE) de forma idempotente: primero verifica si existen y sólo inserta cuando faltan, reduciendo efectos colaterales por reinicios o reprovisionamiento.

5.7 Concurrencia, persistencia y gestión del estado

El orquestador mantiene un estado global en memoria protegido por un RLock (sección crítica), y lo persiste de manera atómica en JSON al actualizar peers/redes o incrementar config_version. Esto permite distribuir cambios por versión y facilita detectar si un peer está desfasado mediante el heartbeat.
